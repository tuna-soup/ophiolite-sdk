# The mapper, version 1 (E116)

`ophiolite-mapper` is the standalone box that turns a well table, a log file, a database table or a bucket of files
into a project folder: typed Parquet, the originals, identity and lineage, and an OSDU manifest. It installs alone
(`pip install ./ophiolite-connectors/mapper`) and needs no Ophiolite service. This folder holds its contract; slice 0
publishes the contract and a command that refuses, and slices 1–5 give it behaviour.

| File | What it is |
|---|---|
| `recipe-schema.json` | `ophiolite.mapper-recipe/1`: the structure of `recipe.json`, which `inspect` writes, a person edits and `write` reads |
| `folder-schema.json` | `ophiolite.project-folder/1`: the `folder` block of a bundle v2 `manifest.json`, the roles of its files, the columns of the identity tables and the keys of the lineage document |
| `reviewed-schema.json` | `ophiolite.mapper-reviewed/1` (1.4): the structure of `ophiolite-reviewed.json`, the column picks and accepted aliases of finished writes that `inspect` brings back for the same table |
| `export-report-schema.json` | `ophiolite.osdu-export-report/1` (1.5): the structure of `osdu/export-report.json`, which an export of a bundle to OSDU records writes: asset to record and payload, masters, unwritten assets with their reasons, declared losses |
| `rules.json` | `ophiolite.mapper-rules/1`: the evidence classes, what applies without a decision, the blocking severities, the refusal order and every sentence, under one `rules_version` |
| `mapper.py` | `ophiolite.mapper-validator/1`, the validator of record: `check_recipe`, `effective`, `refusal`, `unacknowledged`, `validate_folder`, `check_tables`, `sentence`, and since 1.4.0 `bundle_refusal`, `refusal_sentence`, `unwritten_entry`, `check_export_report`; standard library only (Python 3.10) |
| `osdu-vocabulary.json` | `ophiolite.osdu-vocabulary/1`: the OSDU data-definitions v0.30.1 kinds, units, unit quantities, curve families and coordinate reference systems the box emits, generated by `../../tools/osdu-vocabulary.py <checkout>` (`--check` names the first difference); since 1.3 also the active well-log sampling domains |
| `osdu/v0.30.1/` | `ophiolite.osdu-schemas/1`: the eight kinds' schemas and every schema their `$ref` reach (56 files of `Generated/`), unmodified, with the Apache-2.0 `LICENSE` and a `NOTICE`; written by the same generator, which refuses a closure that is not exactly its pin |
| `osdu_schema.py` | `ophiolite.osdu-schema-validator/1`: the offline check of a record or manifest against `osdu/v0.30.1/`, standard library only, applying exactly the draft-07 keywords that closure uses and refusing any other |
| `export-matrix.json` | `ophiolite.osdu-export-matrix/1`: per reader profile and table target, the OSDU kind it would export as (or why none), the declarations it needs and its typed differences; `written_by_box` only for `las2/1` and the wells table; generated by `../../tools/export-matrix.py` |
| `osdu_kind.py` | E168 s0 (D6): `lookup(profile)` and `pair(profile)`, the `osdu_kind` / `osdu_kind_reason` an answer or a profile document carries, read from `export-matrix.json` (a profile without a row: `no correspondence declared`); read by the gateway, the contract generator and the SDK's synced copy |
| `fixtures/` | valid recipes and folder blocks, single-defect cases with their expected codes, the effective-recipe table, the refusal order, acknowledgement binding and synthetic identity rows |

**One validator.** The Platform tests and the box run this same `mapper.py`; the box carries byte-identical copies of
it, the two schemas, `rules.json`, `osdu-vocabulary.json` and `../../vocabulary/v1/mapping-check-words.json` in
`ophiolite_mapper/contract/`. `mapper.py` applies the schemas' keywords itself (no `jsonschema` needed) and adds the
rules a schema cannot state; a date-time is checked as RFC 3339 with a zone, since JSON Schema's `format` is only an
annotation.

**Decisions are authority; findings are a snapshot.** A recipe's decisions (`accept`, `choose`, `leave-unmapped`,
`accept-alias`, `reject-alias`, `new-entity`, `reject`) say what `write` applies. What applies without a decision
depends on the evidence: `declared`, `previously-reviewed` and `project-default` values apply, `inferred` and `none`
do not, and a required field, an inferred declaration, an inferred layout or a well matched only by normalising its
name must be decided first. Findings are what `inspect` saw. `write` recomputes them with the table engine over the
effective mapping; a severity always comes from `mapping-check-words.json`, and an acknowledgement applies only to a
finding with the same field, code and number of rows. An acknowledged finding's rows are left out of the folder and
counted; no acknowledgement writes a row that has an `invalid` or `not-supported` finding.

**Two validators, two readers (1.3, E116 s3).** `mapper.py` judges recipes and folder blocks against this folder's
schemas; `osdu_schema.py` judges OSDU records against the vendored data-definitions schemas, and neither reads the
other's. `osdu_schema.py` follows a `$ref` only to a file inside `osdu/v0.30.1/Generated/` (a URL or a path leaving it
refuses), ignores a `$ref`'s siblings as draft-07 does, treats `format` as an annotation, and refuses a keyword it does
not apply, so a schema it cannot apply exactly never passes in silence. The Platform tests compare its verdicts with
`jsonschema` on the same files.

**Missing markers mean "any of".** A recipe's `missing` (for the whole table) and `columns[<label>].missing` are lists:
a cell equal to any marker of its column or of the table is missing. `write` replaces each such cell with the empty
cell before the table engine sees the rows, and gives the engine the mapping without markers; a missing value is
written as null, never as the marker.

**What inspect writes (rules 1.1.0).** `inspect` reports the table engine's suggestion and applies none of it: every
row of the recipe it writes carries the evidence it saw and `decision: null`, and its check is the engine's over the
suggested mapping, as if every suggestion were accepted. Its refusals (`rules.json` `inspect`, in that order) write
nothing; an existing recipe is replaced only when asked. In a wells table every row is its own well, so `wells[]`
lists only names that resemble each other after normalising. Since 1.2.0 an accepted alias merges its row into the
canonical row's well when their identifiers are equal and every other mapped field agrees (`alias-conflict` names the
first that does not).

**Identity is a decision (rules 1.2.0, E116 s2).** A recipe for a table of wells or a LAS profile (`rules.json`
`identity_targets`) carries `identity` — `basis` `external` (ids from the column `column`, the one mapped to `id`) or
`provisional` (ids from the keys written in `wells[]`) — and `write` refuses `identity-undecided` until it is accepted.
In a LAS profile every spelling has a row: an `exact` row needs `new-entity`, whose entity is the wellbore the `WELL`
header names, with `well` the key of its well (edit it for a sidetrack); a well entity has no `well`. A recipe made with
other rules refuses `recipe-outdated` before it is judged by these ones.

**A folder of LAS files (1.2).** Source kind `folder` (a local directory, digest `over: members`); the folder's
originals are `text/plain`, and the item of a reader profile is the stem `folder-schema.json` `profile_items` names
(`items/well-log.parquet` for `las2/1`, its columns under `items`). `check_tables` refuses an entity id listed twice
(`entity-repeated`). A folder written by slice 1 still validates.

**A folder the box writes alone (1.1, bundle 2.12).** Its manifest lists no assets and no selection; the folder block
carries role `original` (`originals/<name>`, the source's own bytes, `text/csv` in slice 1) and role `item`
(`items/<target>.parquet`, the typed table of one target, the stem the recipe's table target), at least one of each
when the manifest lists no assets, beside `recipe.json` and `lineage/prov.json`. `validate_folder(block, manifest,
recipe)` binds every item to the recipe's target once the recipe's bytes are verified. Beside server assets the two
roles are optional and `representation` keeps its meaning.

**Workbooks, earlier picks and buckets (1.4, rules 1.3.0, folder 1.3, E116 s4).** A recipe for a file named `.xlsx`,
`.xlsm` or `.xls` carries `reading` rows, at least `sheet` and `header_row` (`rules.json` `reading`); no other source
kind carries them. `sheet` is `declared` (the workbook has one sheet, or the person named one) or `none` (the person
must name it); `header_row` is `declared` or `inferred`; a row that is not `declared` applies only once accepted, and
`write` refuses `reading-undecided` until then. A field whose evidence is `previously-reviewed` says where the pick came
from (`reuse`: `same-table`, the same file or prefix, sheet and columns; `similar`, another table with the same columns)
and how it applies (`apply`: `prefilled` applies without a decision, `offered` waits for one, as the Workspace's second
import does); a similar table's pick is only ever offered. `check_reviewed` validates `ophiolite-reviewed.json`: one
pick per target, table and schema digest (the SHA-256 of the canonical list of column names and types), one alias per
target and spelling, at most a thousand of each. Originals may be Excel workbooks with their own media type. A bucket
prefix names its `region`, ends in `/` (or is empty), and may use plain `http` only to `127.0.0.1:<port>`; a 1.2.0
recipe still refuses `recipe-outdated`.

**An exported bundle (1.5, rules 1.4.0, E169 s0).** Source kind `bundle` (a `portable-bundle/2` export of an Ophiolite
project, read by reader `portable-bundle/2`), located like a file; its digest is `over: bytes` when the path names a
`.zip` (in any case) and `over: members` when it names a folder. Its only target is `osdu-records` with id
`export-matrix`, and only a bundle has that target. A bundle recipe decides nothing: no layout, identity, fields,
columns, declarations, missing markers, wells or findings, because the bundle carries identity, units and nulls as
exported; manifest's refusals are the command's, never findings. `bundle_refusal(recipe, digest_now, facts)` gives
the first of `rules.json` `manifest_refusal_order` from what the box's bundle reader found (handed over as data: a
reason it could not read, whether the path is a project folder, whether wells were exported, and per log and wellbore
how many associations it has; a count other than one refuses, no edge is chosen by position), and
`refusal_sentence` words it from the closed lists `bundle_unreadable` and `association_things`. The export report
(`export-report-schema.json`, `ophiolite.osdu-export-report/1`, written as `osdu/export-report.json`) says which asset
and revision became which record and payload (`originals/<asset id>.las`), with the source system it came from, the
masters made from the bundle's wells and wellbores, every asset left unwritten with a reason from `rules.json`
`unwritten` and that reason's sentence (the export matrix's own reason, which names OSDU kinds, only in `detail`), and
every declared loss; `check_export_report` holds that records and unwritten partition the bundle's assets, that each
list's `empty` flag is stated, and that the counts per kind are the masters' and records'. A 1.3.0 recipe refuses
`recipe-outdated`. In this version the box recognises a bundle and refuses; writing records is the next slice's.

**A curve LAS cannot name (1.6, rules 1.5.0, E169 s1).** A log is written as one LAS 2.0 file, whose header line
ends a mnemonic at its first dot and a unit at its first space; a log with a curve whose name or unit such a line
cannot carry is left unwritten with the reason `curve-text-unwritable`, its sentence asks for the curve to be renamed,
and the report's `detail` names the curve. Nothing else changes; a 1.4.0 recipe refuses `recipe-outdated`.

**No credentials in a recipe.** A file is named by its path, a database table by the name of a source configured on
the person's computer plus its schema and table, and a bucket by an `https` endpoint without a user, password, query
or fragment, its bucket and its prefix.

**Identity follows E20.** `part-of` runs from a wellbore to its well; `of-entity` from a representation's payload
(`sha256:<hex>`) to its well or wellbore. Entity ids come from the recipe's decisions, never from measurements, so a
changed measurement changes only the payloads.
